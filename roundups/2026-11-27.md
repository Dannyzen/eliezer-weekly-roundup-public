# Friday Synthesis: 2026-11-27

## Weekly thesis

Agent reliability is becoming a systems property. The strongest work this week moves trust out of model self-report and into explicit runtime state, independent evidence, effect mediation, and operating-condition-aware evaluation.

A useful control plane now needs four inspectable objects: the state an agent resumes from, the authority it may exercise, the concrete effects it attempts, and the evidence used to accept the result. A strong model helps, but it cannot repair hidden state loss, forged attribution, evaluator contamination, or a benchmark with no real routing headroom.

## 1. Persistent state must preserve task truth and authority separately

[CompAct-Bench](https://arxiv.org/abs/2611.25673v1) evaluates compaction by letting an executor continue the task after a controlled compression boundary. Its important result is qualitative as well as quantitative: compactors can turn unresolved issues into apparent conclusions or forget established results. [LLM Agent Authorization Across Context Compaction](https://arxiv.org/abs/2611.32194v1) shows the security version of the same failure. A model-written summary can make injected data look user-authored unless authenticated user text crosses the boundary separately.

The design consequence is direct: summaries are working context, not authority records. Persist task state, unresolved obligations, provenance, and authenticated intent as typed objects outside the summary. Test them by resuming real tasks, not by judging summary fluency.

Implementable now:
- store authenticated user intent and policy inputs separately from model summaries
- add unresolved, established, and superseded status to durable task facts
- replay post-compaction continuations against uncompacted controls
- use Pi 1.6 tool parks for durable waits that release the active invocation

Implementability score: **0.72**

Core sources: [CompAct-Bench](https://arxiv.org/abs/2611.25673v1), [Authorization Across Context Compaction](https://arxiv.org/abs/2611.32194v1), [Cloudflare Pi 1.6 tool parks](https://developers.cloudflare.com/changelog/post/2026-11-20-pi-harness-pi-1-6/)

## 2. Evaluation must model the deployed system, not only the model

[MASSys](https://arxiv.org/abs/2611.28671v1) shows that the same multi-agent workflow can change rank under a different serving substrate or load regime. [ShellBench](https://arxiv.org/abs/2611.32946v1) crosses models, harnesses, and reasoning levels over 53,100 rollouts. Hugging Face's [agentic evaluation guide](https://huggingface.co/blog/agentic-evals) treats tasks, environments, traces, and graders as maintained infrastructure.

The combined lesson is stronger than “run more benchmarks.” Report the configuration tuple and operational denominator: model, harness, reasoning budget, substrate, load, delivered tasks, latency, cost, failures, and grader identity. A benchmark score without those dimensions is a property of an unnamed system.

Implementable now:
- pin model, harness, prompt, tools, grader, substrate, and load in every result record
- preserve failed and timed-out submissions in the denominator
- isolate graders from agent-controlled files and tests
- maintain eval fixtures and traces as versioned artifacts

Implementability score: **0.88**

Core sources: [MASSys](https://arxiv.org/abs/2611.28671v1), [ShellBench](https://arxiv.org/abs/2611.32946v1), [How to build and maintain an agentic evaluation](https://huggingface.co/blog/agentic-evals)

## 3. Side effects need enforcement below the tool-call narrative

[AgentBouncer](https://arxiv.org/abs/2611.30621v1) mediates system calls triggered by agent tools, because a benign-looking tool call can still produce a dangerous concrete effect. [AgentLens](https://arxiv.org/abs/2611.34380v1) adds the audit side: static findings become meaningful only when a realistic executable path triggers them. Together they define a practical safety boundary below prompts and tool schemas.

The strongest objection is cost and complexity. System-call mediation can add latency, platform coupling, and policy false positives. That cost is survivable at privileged boundaries. Start with deterministic deny rules and explicit capability grants, then invoke learned arbitration only for ambiguous high-impact effects.

Implementable now:
- run privileged tools in isolated workers with explicit filesystem, network, and process grants
- record attempted effects independently from model explanations
- validate high-severity findings with bounded executable scenarios
- require receipts for writes, network calls, credential use, and process execution

Implementability score: **0.48**

Core sources: [AgentBouncer](https://arxiv.org/abs/2611.30621v1), [AgentLens](https://arxiv.org/abs/2611.34380v1)

## 4. Verification should produce evidence, not a confidence number

[Agent-as-a-Verifier](https://arxiv.org/abs/2611.34132v1) replaces a scalar judgment with a claim graph, an independently compiled acceptance contract, checkable obligations, and evidence certificates. The implementation pattern matters more than the paper's benchmark lead: release decisions can inspect what was checked, what evidence supports it, and where uncertainty remains.

This also changes how human feedback should be used. Operator replies and benchmark grades are evidence candidates with provenance. They should not silently become policy or training truth.

Implementable now:
- compile acceptance criteria independently from the candidate output
- split claims into checkable obligations
- attach commands, artifacts, source identities, and results to each obligation
- fail closed when a required obligation lacks evidence

Implementability score: **0.74**

Core source: [Agent-as-a-Verifier](https://arxiv.org/abs/2611.34132v1), [General-Verifier repository](https://github.com/sunyxedu/General-Verifier)

## 5. Optimization needs causal diagnostics before intervention

Two late-week findings sharpened the same rule. [Delta Residue Attribution](https://arxiv.org/abs/2611.34875v1) tests patch units by reverting them and rerunning tests, showing why patch size is a poor proxy for over-editing. [RouteabilityBench](https://arxiv.org/abs/2611.34825v1) asks whether a benchmark and model portfolio contain enough prompt-specific variation to justify routing at all.

The practical principle is: measure whether the optimization target exists before building the optimizer. For patches, test necessity. For memory, locate the stage where evidence disappeared. For routing, quantify oracle headroom, ties, and predictor separability.

Implementable now:
- add mutation or block-reversion checks to coding-agent release gates
- score memory retrieval, consolidation, reflection, and answer stages separately
- audit routeability before deploying a learned router
- keep a single strong model as the fail-closed baseline

Implementability score: **0.78**

Core sources: [Delta Residue Attribution](https://arxiv.org/abs/2611.34875v1), [Routeability Before Routing](https://arxiv.org/abs/2611.34825v1)

## What to build first

1. **Record** the complete execution tuple and failed-job denominator for every agent run.
2. **Separate** authenticated intent and policy from summaries and operator prose.
3. **Compile** acceptance criteria into claim-level evidence obligations.
4. **Mediate** privileged effects in an isolated worker with deterministic rules first.
5. **Optimize** memory, patches, or routing only after a causal audit proves headroom.

## Strategic conclusion

The week argues for an evidence-bearing runtime, not a smarter conversation wrapper. Context may remain probabilistic and editable. Authority, effects, and acceptance evidence need typed identities, explicit boundaries, and replayable receipts.

The provocative question is whether the agent platform should treat summaries, tool calls, and scores as views over canonical runtime objects rather than canonical state themselves. The evidence this week says yes.
