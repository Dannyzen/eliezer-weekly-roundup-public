# Friday Synthesis - 2026-09-04

## Thesis

Observed success is not authorization.

This week, research on dual oracles, serving-interface censoring, skill policy theft, lifecycle-hook admission, plan lineage, and capability isolation converged on the same design rule: a green functional test, a parsed tool-call rate, a current replica, a valid OAuth token, a declared skill interface, and a trusted plugin can all be true while the runtime is already wrong. Observations may change representation. They must not silently become acceptance, authority, or proof.

## Week-level findings

### 1. Acceptance needs a second oracle

SWE-Gate split repository repair into a functional suite and an executable review-constraint suite. Across 303 instances from 75 Python repositories, 221 of 644 functionally successful repairs failed the constraint tests, a 34.3% hidden-failure rate. GPT-5.5 reached 74.9% functional success and 52.8% joint success. Providing the constraint text raised joint success, not functional success.

LoopArena made the same split at the loop layer: fix the worker, evaluate the controller. The best full-task Strict Success Rate was 24.69%. Condensed evaluation cut estimated inference cost by 64.4% and preserved controller ordering. EarlyEval then showed that once a trajectory already predicts the outcome, paying for the tail is optional: 13% to 26% fewer steps and up to 44.1% fewer input tokens, with about 1 to 2 point resolve-rate movement.

What changed: a resolve rate is an observation. Acceptance is a pair of oracles, one for the reported issue and one for the review, controller, or trajectory constraint that production actually cares about.

Implementable now:
- keep separate functional and constraint oracles, plus a non-compliant reference that proves they are not the same test;
- report FSR, CFR, JSR, and hidden-failure rate instead of a single resolve rate;
- evaluate runtime controllers separately from fixed workers on cheap fixtures and full-task anchors;
- halt eval once a calibrated prefix predictor already knows the ending.

Implementability score: 0.74

### 2. The measurement instrument can delete the evidence

Interface-Induced Trajectory Censoring held weights, cases, executor, scorer, decoding, and seeds fixed, then changed only the serving adapter. On BFCL v4 the same model moved from 0.00 to 0.96 / 0.19. Template and parser main effects were zero; the interaction was the entire effect. Qwen2.5-Coder 32B emitted 80/100 well-formed calls while the server parsed 0/100. GRPO could raise pass@1 while multi-turn rescues stayed flat, and a function-calling GRPO run could execute zero tools while the critic reward climbed.

BTS-AgentBench supplied the complementary compiler: checksummed source records, a read-only tool store, typed multi-turn tasks, tool-derived gold evidence, and two-build replay proof. The 532-row release reproduced its 356/87/89 split exactly. Hermes v0.21 made continuity and orchestration inspectable runtime surfaces rather than ambient chat state.

What changed: eval dashboards and RL critics will both look healthy while the branch being measured does not exist. The serving adapter, parser, and telemetry compiler are part of the instrument.

Implementable now:
- log raw model bytes, parser output, and executor admissions as three separate counters;
- fail closed when HTTP 200 returns empty `tool_calls` but the completion contains a well-formed call;
- compile operational records into deterministic, replayable evaluation episodes before model judging;
- treat continuity contracts as explicit, inspectable state with provenance and expiry.

Implementability score: 0.80

### 3. Declared interfaces are delayed policy, not authority

SkillShift kept the declared task and a valid output interface while steering shopping and dependency choices. Preference-shift rate rose to 81.33% in shopping and 63.33% in Python dependencies at 100% valid-output rate. Static scanners that catch direct injection missed the stealth pair.

Defense-as-Skill showed the complementary control: an installable Markdown guard that sits beside untrusted task skills, checks proposed actions against the current user task, and returns allow, replan, or confirmation. On Claude Code with GLM-5, N = 10, in-distribution attack success fell from 0.482 to 0.104. Adding an allowlist to AcceptEdits collapsed protection. The guard is still instruction-following, so it complements sandboxes and permission brokers rather than replacing them.

HookPry then skipped the model. Lifecycle hooks run host-privileged commands as configuration, including at times the LLM never observes. Across seven harnesses and 1,000 end-to-end runs, verified E2E-ASR was 77.9% macro-average. Hermes was 92.5%. Claude Code was 52.5%. Privilege Escalation averaged 93.5%. Native hooks beat translated MCP descriptions (92.0% vs 56.0% on the paired 50-target set).

What changed: install review, marketplace sync, and hook mutation are three different authority events. Scanner verdicts and declared skill interfaces are not frozen policy. A command that never entered the LLM trace is still an effect.

Implementable now:
- audit skills with paired clean/attack selection fixtures, not scanner verdicts alone;
- treat loaded skills as delayed-authority objects with a task-conditioned consult-before-action guard;
- pin hook command hashes at admission and treat plugin update as a new admission;
- emit hook-event receipts even when the model is out of the loop;
- keep hard brokers for host effects.

Implementability score: 0.62

### 4. Freshness is not lineage

PlanFence distinguished replica freshness from lineage validity. Plans cite exact parent record IDs. The executor validates only action-relevant parents, then replans or blocks. In 30 live workflows with a post-plan revision, freshness-only execution issued the obsolete action every time (0/30). PlanFence completed all 30 without an invalid action.

ACLE-MCP named the same gap one layer down: a remote MCP call can keep OAuth and still run on the wrong workload. A short-lived, sender-constrained capability lease is consumed by an Execution Gate before protected tool logic. In the local simulation, OAuth-only and connect-time attestation blocked none of six misuse families.

CIPR showed the repository side: poisoning risk depends on how the user invokes the agent. Trusted invocations activate untrusted repository paths. Memory accounting this week made the same identity point: stored state, delivered context, management work, and task outcome are four different objects, and equal token budgets do not imply equal delivered context.

What changed: "latest" is not an authorization object. Record IDs, workload leases, invocation plans, and typed memory layers are.

Implementable now:
- stamp every plan with exact parent record IDs, not "latest requirement";
- validate only action-relevant parents at the effect gate;
- bind remote tool calls to invocation-scoped workload leases instead of connect-time OAuth;
- treat the user invocation as an activation plan over untrusted repository content;
- measure memory as stored state, delivered context, management work, and outcome.

Implementability score: 0.58

### 5. Isolate capabilities at the resource, not the model

The week's highest-implementability findings were not new models. They were destination allowlists and resource-identity permission checks. Prompt-injection work showed that removing outbound capabilities from components that read untrusted content, then enforcing destinations and data classes outside the model, remains the cheap control. Permission checks that bind to the exact resource, model, route, and configuration used scored 0.97. User policy as preference, not standing authorization, scored 0.84.

What changed: asking the model to recognize injection, or asking a plugin marketplace to stay trusted, is the wrong layer. The resource actually used, the destination actually reached, and the effect actually released are the objects that can be checked.

Implementable now:
- bind permission checks to the exact resource, model, route, and configuration used;
- remove outbound capabilities from components that read untrusted content;
- enforce destinations, data classes, and typed effects outside the model;
- keep user preference, standing policy, and exact-effect authorization as three separate objects.

Implementability score: 0.91

## The stack after this week

1. Observe: keep raw completions, traces, and operational records intact.
2. Compile: turn telemetry into deterministic episodes before judging.
3. Challenge: add a second oracle for review constraints, controller quality, or trajectory evidence.
4. Bound: treat skills and hooks as delayed-authority objects with task-conditioned guards and hashed admission.
5. Identify: bind plans, leases, and invocations to exact parent IDs and workload identities.
6. Isolate: check the resource used and the destination reached, not the model's explanation.

The recurring failure is silent substitution. A functional test stands in for review. A parsed empty array stands in for no tool use. A current replica stands in for a valid plan. A declared skill stands in for frozen policy. A trusted plugin stands in for hook admission. The runtime must make each substitution explicit and reversible.

## Implementability range

The week's highest assigned score was 0.97 for permission checks bound to the resource actually used. The lowest was 0.48 for invocation-scoped MCP workload leases, which remain architecture-heavy and simulation-backed.

## Strongest objection

Dual oracles, hook pinning, parent-ID validation, and serving-adapter counters add fixtures, durable state, and more failure modes in the control plane itself. Several papers are new preprints. HookPry and PlanFence expose no public implementation repository. That is survivable because the first implementation does not require a universal runtime. Start with one coding-agent acceptance pair, one serving-adapter 2x2, and one hook-update admission. Keep only controls that catch hidden failures or blocked effects without unacceptable false holds.
